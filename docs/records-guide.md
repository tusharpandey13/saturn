# Records guide: how to keep a records repo

Saturn keeps a household's health records in a separate, private **records repo** (`<records-repo>`, [ADR 008](decisions/008-product-environment-pii.md)). This guide is the generic rule set for every agent and human who writes in one. A records repo copies it into its own `AGENTS.md` and adds local choices (people, languages, review cadence). Where a newer instruction from the records owner conflicts with that file, the owner wins; record the change there.

## 0. The three non-negotiables

1. **Record and flag only.** Never diagnose. Never suggest starting, stopping or changing a medicine or dose. Phrase concerns as questions for the named doctor. Every health page carries the line "Facts as written; not advice; doctors decide."
2. **Go-live gate.** No real data reaches any deployment (Worker, D1, R2, agent jobs) until the records owner explicitly says "go" ([deploy runbook](platform/deploy.md)). Record the decision, with its date, in the env repo's status page and an ADR note there. Until then, deployments see synthetic data only.
3. **No secrets anywhere.** Secret values live only in the env repo's encrypted store (SOPS) or in local files outside every repo (mode 0600), and are pushed without echoing. Never write them in docs, commits, chat or logs. A records repo holds no secrets at all.

## 1. Source of truth

- **The structured KB in `data/` is the source of truth** ([ADR 007](decisions/007-simplified-clinical-data-model.md), amending ADR 004). Rows are `source`, `fact` and `ref`, validated against the product `schema/` by `tools/kb/build`.
- **Curated pages are views.** Each clinical row on a curated page cites a KB id. Tables between `<!-- gen:NAME start -->` and `<!-- gen:NAME end -->` (timeline, medicines, labs, data quality, summary glance) are generated by `tools/kb/gen-views`; never hand-edit inside them. Where no KB row exists yet, cite the source path (and page). When the KB row lands, swap the path for the id.
- **Raw inputs** in `sources/` are never edited.
- **`records.yaml`** at the repo root declares `schema_version` (7 = ADR 007), `namespaces:` (one per person plus `family`, with display names) and `d1_person_map:` (D1 person id → namespace, where they differ; every D1 person is a `member` or `admin`, ADR 009). The product reads these; it never hard-codes people.
- **`aliases:`** in `records.yaml` (`<ns>: [names]`) are the name prefixes that record a message for another member ("maa 116/47"). **`data/telegram/subject-overrides.ndjson`** re-attributes one Telegram update (`update_id`, `subject` ns, `set_by`, `set_at`, `reason`); append-only, the latest `set_at` wins; the batch also appends the admin's `/for` corrections here (ADR 009).
- **Telegram output (ADR 011):** the group is input-only; the bot never posts there. The digest, questions and ops alerts go to the admins by private DM, in English. Never ask the family to retype or resend values. Photos are classified first; a non-health photo is a source with `class=non-health` (tag `non-health`) and no facts.
- **Life context (ADR 010):** `context_consent:` in `records.yaml` (`<ns>: true | false | pending`) gates life-context signals per member; only `true` is read, and nothing is recorded about anyone else. A message starting with `/private` is archived raw and never extracted (no health facts, no context). Context facts are `event` facts with `data.type = context` (summaries only, `quote` null, `unverified`, `data_class: phi`). With env `context_mode: shadow` they carry the tag `shadow`, are hidden from every view and appear only in the admin's digest DM; with `on` they render in the `gen:context` block of `timeline.md` (admin-only by convention). A doctor brief uses a context row only when it carries the tag `brief-relevant` (added by a human in a superseding row), and only with association wording ("around the same dates", never a cause).

## 2. IDs

Format: `<ns>:<class>:<local>`. `ns` is one of the `namespaces` in `records.yaml`; reference rows use ns `ref`. Examples use the synthetic family in `fixtures/records-example/` (`alice`, `bob`, `family`).

| Where | Classes | Example |
|---|---|---|
| KB (ADR 007) | `src` source, `fact` (observation, medication, condition, event), `ref:drug` / `ref:code` / `ref:party` | `alice:src:2026-01-15-example-lab-cbc`, `alice:fact:2026-01-15-example-lab-cbc.haemoglobin`, `ref:drug:exampledrug`, `ref:party:example-hospital` |
| Docs register (not in the KB) | `q` question, `ans` answer, `act` to-do; local is a 4-digit number | `alice:q:0001`, `bob:ans:0002`, `family:act:0001` |

- IDs are stable. Never renumber or reuse one. A new item takes the next free number in its `ns:class`.
- Questions (`q`) live in `docs/health/<ns>/questions.md`. To-dos (`act`) live in `docs/health/family/actions.md`. Answers (`ans`) sit with the question they answer.
- When a schema migration renames ids, the migration writes an id map under `data/meta/`; keep it.

## 3. Where things go (records repo layout)

| What | Where |
|---|---|
| Raw inputs | `sources/<ns>/{documents,media/<channel>}/` (ADR 003; raw videos stay out of git, in `<media-dir>`) |
| Structured facts | `data/<ns>/docs/<source-id>.ndjson`; run the build (section 9) before committing |
| Current health state (curated) | `docs/health/<ns>/` only: `summary`, `medications`, `problems`, `timeline`, `care-team`, `questions`, `briefs/`, `research/` (dated cross-references, [method](methods/research-crossref.md); `research/private/` for private-mode runs, with a gitignored `.cache/` for restricted PDFs) |
| Household to-dos | `docs/health/family/actions.md` |
| Extraction notes, hard-reads, chat triage, analyses | `docs/log/…` (dated, append-only) |
| Cross-check flags and claims register (ADR 012) | `crossref/` (checks, owner feedback, derived flag and claim state, run log) and the generated `docs/health/<ns>/flags.md`, `claims.md`; written by `tools/crossref` ([README](../tools/crossref/README.md)); give feedback with its `feedback` command |
| Records-local config | `records.yaml`, `config/thresholds.yaml` (optional red-flag thresholds, below), `meta/stt-vocab.txt` (optional STT vocabulary), `meta/extraction-context.md` (optional extraction context), the denylist and the docs-site sanitiser |

### `config/thresholds.yaml` (red-flag thresholds)

The product ships the rule engine but **no clinical values**. The values that turn readings and symptoms into digest annotations live in the records repo, in `config/thresholds.yaml`, because they are clinical choices for these people and belong with their doctor.

- **Absent:** the rules are disabled. The digest shows no annotations (the batch log says thresholds are not configured).
- **Present:** validated against the product schema (`app/src/config/thresholds.ts`: same camelCase keys, numbers where numbers are expected). Unknown keys, wrong types, duplicate keys or bad YAML stop the batch with an error naming the key (fail closed); nothing runs on half-read thresholds.
- **Header fields:** `version`, `status` (`pending_clinician_signoff` or `signed_off`), `setBy`, `effectiveFrom` (`YYYY-MM-DD`). The digest prints the status next to every annotation.
- **Changing values:** edit the file, bump `version`, set `setBy` and `effectiveFrom`, commit. Set `status: signed_off` only after the treating clinician has reviewed the values; until then keep `pending_clinician_signoff` and write "unverified; doctor sign-off pending" in the header comment. Cite the source of each value in a comment (guideline or doctor), and mark any value without a source `PLACEHOLDER`.
- **Shape:** see the synthetic example `fixtures/records-example/config/thresholds.yaml` (example values for tests; not clinical guidance).

Technical state, run history and deploy decisions belong in the env repo, not here. Product decisions belong in the product `docs/decisions/`.

Never create a new list of questions, to-dos or gaps. Add to `questions.md` or `family/actions.md`.

## 4. Naming and dating

- Files: `YYYY-MM-DD-<facility>-<what>.<ext>` (source date, not ingest date). OCR sidecars: `<same>.ocr.md`. Log notes: `YYYY-MM-DD-<slug>.md`.
- In text, dates are `DD-Mon-YYYY` (15-Jan-2026). Front matter uses ISO. State the time zone once per records repo.
- Paths use namespaces. Family nicknames appear only in family-facing prose.

## 5. Curated pages

- Use the templates in [meta/templates.md](meta/templates.md). Front matter: `title`, `audience`, `type`, `owner`, `last_reviewed`, `review_every`, `status`, `sources` (KB ids or paths), `generated`.
- Overwrite in place; git is the history. `timeline.md` carries clinically meaningful changes.
- Where sources disagree, write `conflict:` and show both. Do not choose.

## 6. Provenance and verification

- Every clinical statement cites a KB id or a source path (+ page). Quote verbatim for values, doses and diagnoses.
- Tag who said it: document / doctor-written / family-reported / patient-reported / agent-inferred. Never present an inference as a fact. Uncertain readings go to a hard-read, not into prose.
- Verification ladder for facts: `unverified` → `agent` → `human` → `patient` → `clinician`.
- **Evidence over recollection.** Documents are the source of truth for analysis. A claim from memory (the owner's, a family member's or an agent's earlier note) is a lead to check, not a premise: find it in the documents and quote it with source, page, author and date, or report plainly that the documents don't support it. Analyses state, per claim, whether the evidence agrees, disagrees or is silent. Earlier agent-inferred statements that new evidence contradicts are corrected explicitly ("Corrected <date>: ..."), never silently edited.
- Medicine status (every line in `medications.md`): `prescribed` / `strip-seen` / `patient-confirmed` / `clinician-reconciled` / `stopped`. A medicine is "current" only when `strip-seen` or better and not contradicted by a later prescription.
  In the KB (ADR 007) these map to `data.status` (prescribed, dispensed, taking, stopped) plus `verification`: `strip-seen` = a strip or box photo checked by a human; `patient-confirmed` = `taking`; `clinician-reconciled` = verification `clinician`.

## 7. Superseding

- KB facts are never edited: add a row with `supersedes`; the old row becomes `superseded` (ADR 007).
- Log notes are never rewritten. Add `Superseded by: <path> (date)` at the top.
- ADRs change status only, with forward links both ways.
- Answered questions move to "Answered" with the answer and its source. Never strike through in place.

## 8. Ingest fan-out (what each new input must update)

| New input | Update |
|---|---|
| Prescription / medicine photo | `medications.md` (+ discrepancies), `timeline.md`, `questions.md`; mark briefs `regenerate: true` |
| Test result / imaging | `timeline.md`, `summary.md` "results pending", `problems.md` if a doctor wrote a diagnosis |
| Visit / admission / event | `timeline.md`, `care-team.md` (last contact), `summary.md` recent events, `family/actions.md` |
| Family / patient report or voice log | `docs/log/extraction/patient-reported/`, then `timeline.md` (tagged family-reported), `questions.md` |
| Answer from the records owner | `questions.md` (move to Answered), and every page the answer changes |

## 9. Definition of done for an ingest

1. Raw file stored with the right name. Hard-to-read items queued in `docs/log/hard-reads/`.
2. Facts added to `data/` (when the KB covers that type), then, from a product checkout,
   `python3 -I tools/kb/build --records <records-dir> && python3 -I tools/kb/gen-views --records <records-dir>`
   passes, and the regenerated pages are committed with the data (`gen-views --records <records-dir> --check` fails on stale pages; records CI runs it).
3. Every page in the section 8 row is updated, cites its source and has its status set. `last_reviewed` changes only after a full re-read.
4. New questions and to-dos get ids; answered ones are moved.
5. Briefs whose inputs changed are marked `regenerate: true`.
6. No PHI outside the section 10 paths; no secrets.
7. Commit `data:` / `docs:` + one-line summary. Rebase on the remote branch, push, report the hash.

## 10. PHI boundaries

- PHI (names, dates of birth, ids, policy or claim numbers, clinical details, media) lives only in the records repo: `sources/`, `data/`, `docs/health/` and `docs/log/`.
- The product repo (code, schema, docs, ADRs, fixtures, issues, PR text) and the env repo carry none. Tests and e2e use synthetic data only (`fixtures/records-example/`), never "anonymised" real data.
- Commit messages in the records repo say what changed, not the clinical detail.
- Anything shared outside the household passes the docs-site denylist gate, with the sanitiser kept in the records repo (`--sanitiser <file>`). Doctor briefs are shared deliberately: one person, one purpose.

## 11. Review cadence (set locally)

Each records repo sets its own cadence in its `AGENTS.md`. Suggested defaults: health pages reviewed within 30 days; medications within 7 days while any line is `prescribed`-only; briefs regenerated within 48 h before a visit; a monthly skim of `questions.md` and `actions.md`.

## 12. Working style

- Heavy work goes to subagents in isolated worktrees; the orchestrator verifies their output.
- Verify claims yourself (run the build; check key values against the page image) before reporting.
- Cost-impact min-max; complexity is debt; state asymmetric risks.
